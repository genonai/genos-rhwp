0. 지금 상태 — 왜 아직 안 보냈나
────────────────────────────────────────────────────────────────

보낼 준비는 다 됐는데 **받을 창구가 닫혀 있다.**

저장소 SECURITY.md 는 제보 채널을 이것 하나로 안내한다:

  "보안 취약점은 공개 이슈로 등록하지 말고 …

그런데 그 기능이 실제로는 꺼져 있다:

  {"message":"Repository does not have private vulnerability reporting enabled",

SECURITY.md 에 이메일 같은 대체 연락처가 없고, Discussions 는 공개라 부적절하며,

  → 다음 할 일: #3803 에 메인테이너 답이 달렸는지, Security 탭에
    "Report a vulnerability" 버튼이 생겼는지 확인. 생겼으면 4절대로 제출.


────────────────────────────────────────────────────────────────
1. 취약점 — 무엇이 문제인가
────────────────────────────────────────────────────────────────

한 줄: 문서가 지정한 글꼴 이름이 파일 경로로 해석된다.

src/renderer/svg.rs 의 find_font_file() 이 글꼴 이름에 확장자를 붙여
탐색 디렉터리에 그대로 이어 붙인다:

    files.push(format!("{}.ttf", name));   // name = 문서 DocInfo 글꼴표에서 온 문자열
    ...
    let path = dir.join(candidate);        // ← `..` 와 경로 구분자를 그대로 해석

name 은 공격자가 문서 안에서 자유롭게 정하는 값이다. `../../…` 을 넣으면
탐색 경로 밖 파일이 열린다.

그리고 --embed-fonts=full (FontEmbedMode::Full) 은 찾은 파일을 파싱 없이
통째로 base64 해서 SVG 에 싣는다. 그래서 결과가 단순한 "파일 열림"이 아니라
파일 내용의 반출이다.

  악성 .hwp/.hwpx → rhwp export-svg --embed-fonts=full → SVG 안에 남의 파일 바이트

rhwp 는 MCP 서버로도 동작하므로(#3630, #3719), 그 SVG 가 그대로 LLM 컨텍스트나
사용자 화면으로 갈 수 있다. 에이전트가 신뢰할 수 없는 문서를 변환하는 흐름이
정확히 이 표면이다.


────────────────────────────────────────────────────────────────
2. 영향 범위 — 과장하지 않기 위해 제약을 먼저
────────────────────────────────────────────────────────────────

임의 파일 전체가 아니다. rhwp 가 확장자를 붙이기 때문에
.ttf / .otf / .ttc / .TTF 로 끝나는 파일에만 닿는다.
(코드에서 후보 이름을 이 네 가지로 만든다.)

그래서 제보 본문에 심각도를 medium 으로 제안했다. /etc/passwd 나 id_rsa 같은
것은 이 경로로 못 읽는다. 다만 폰트 파일 자체가 라이선스·내부 자산인 경우가
있고, 존재 여부 확인(파일 오라클)로도 쓸 수 있다.

--font-path 옵션이 필요하지 않다. 이게 중요하다.
renderer/font_paths.rs 의 search_dirs() 는 호출자가 준 경로가 없어도
항상 다음을 탐색 목록에 넣는다:

    dirs.extend(env_font_paths());
    dirs.extend(system_font_dirs());              // Windows: C:\Windows\Fonts
                                                  // macOS:  /Library/Fonts 등
                                                  // Linux:  /usr/share/fonts 등
    dirs.push(PathBuf::from("ttfs/opensource"));  // 번들 최후 폴백

따라서 아무 옵션 없이도 C:\Windows\Fonts 같은 실재 디렉터리에서 `..` 로
빠져나갈 수 있다. 기본 설정에서 성립한다.

  ※ 주의 — 첨부한 재현 테스트 2건은 --font-path 를 명시해서 돌린다.
    그건 취약점 조건이 아니라 시험을 결정적으로 만들기 위한 것이다
    (기계마다 다른 시스템 폰트 배치에 의존하지 않으려고 임시 폴더를 탐색
    경로로 지정한다). 이 구분을 제보할 때 흐리지 말 것 — 실제 조건보다
    까다롭게 들리면 심각도가 과소평가되고, 반대로 뭉뚱그리면 부정확해진다.


────────────────────────────────────────────────────────────────
3. 파일 안내
────────────────────────────────────────────────────────────────

  advisory.json   GitHub Security Advisory 제보 본문. 그대로 POST 하면 된다.
                  summary / description / severity(medium) /
                  vulnerabilities[] (package=rhwp, <=0.8.2, find_font_file).
                  description 안에 제안 패치가 diff 로 들어 있다.

  s5_patch.diff   제안 패치. src/renderer/svg.rs 에 두 곳을 더한다.
                  ① is_plain_file_name() 헬퍼 신설
                     std::path::Component::Normal 하나로만 이루어진 상대
                     이름만 통과. `..`·`.`·루트·`C:` 드라이브 접두사·구분자가
                     든 다단 경로가 전부 걸러진다.
                  ② find_font_file() 의 후보 목록에 files.retain(...) 한 줄.
                  실제 글꼴 이름에는 구분자도 `..` 도 없으므로 기능 손실 0.
                  (같은 계약을 외부 그림 경로는 이미 지킨다 —
                   model/document.rs 의 basename 축약.)

  README.txt      이 파일.

5. 재현 테스트는 어디에 있나 (공개 금지)
────────────────────────────────────────────────────────────────

로컬 git 브랜치 pr/sec-boundary-proof 에만 있다.
tests/boundary_integrity_contract.rs 의 두 건:

  font_name_cannot_escape_the_font_search_dir
      임시 폴더에 탐색 경로 안 글꼴(rhwpallowed.ttf)과
      밖 비밀 파일(rhwpsecret.ttf)을 만든다.
      ① 양성 대조 — "rhwpallowed" 는 실제로 임베딩된다(base64 가 SVG 에 있다).
         이 대조가 없으면 임베딩 경로가 죽어 있을 때 음성 판정이 공허해진다.
      ② 본 시험 — "../rhwpsecret" 은 SVG 에 들어가면 안 된다.
         base64 와 평문 양쪽으로 확인한다.

  absolute_and_nested_font_names_are_rejected
      절대 경로·다단 경로 이름도 같은 문에서 막히는지.

  (rewrite_font_faces 는 HWPX 의 글꼴 이름을 갈아 끼우는 헬퍼다.)

  ⚠ 이 브랜치를 fork 에 push 하지 말 것. 원격 브랜치는 노출 때문에 이미 지웠다.
    확인: git ls-remote --heads fork | grep sec-boundary-proof → 0건이어야 한다.

7. 어떻게 발견했나 (배경)
────────────────────────────────────────────────────────────────

이슈 #3787(에이전트 보안) 의 S5 "경로는 문서 내용에서 파생되지 않는다" 를
증명하려다 나왔다. 산출 경로(-o, output/)는 조사 결과 처음부터 안전했다 —
본문에 traversal 문자열을 심고 export 축 4개를 돌려도 산출물은 -o 안에만
생긴다. 그런데 "문서에서 온 문자열이 파일 경로가 되는 자리"를 넓게 훑다가
글꼴 이름 경로를 찾았다.

같은 조사에서 나온 별건 하나는 취약점이 아니라고 판정했다:
rhwp run 이 계획의 output 에 `..` 을 받아 그 위치에 쓴다(재현함). 하지만
그건 호출자가 계획 파일에 적은 경로라 `-o ../../x` 와 같은 부류다. 문서
본문에 경로 문자열을 심어도 산출은 계획 지정 경로에만 생기는 것을 실측으로
확인했다. 정화기를 넣으면 정당한 상대 경로가 깨지는 동작 회귀라 넣지 않았다.

  ※ 조사 중 "batch fill --name-field 의 sanitize_output_stem 과 비대칭"이라는
    단서를 받았지만 검증 불가로 근거에서 뺐다 — 그 심볼이 base(devel
    a8d7bdfb)에 grep 0건이고 미머지 브랜치 코드였다. 근거로 쓰지 않았다.
